## (a) HSK 2–6 — data already present, lessons need wiring

### Existing data format (`public/data/hsk/`)

```
public/data/hsk/
├── index.json          // { source, note, levels: [{level, count, file}, ...] }
├── 1.json              // { level: 1, source, license, count: 150, items: [...] }
├── 2.json              // { level: 2, count: 151, items: [...] }
├── 3.json              // { level: 3, count: 300, items: [...] }
├── 4.json              // { level: 4, count: 600, items: [...] }
├── 5.json              // { level: 5, count: 1300, items: [...] }
└── 6.json              // { level: 6, count: 2500, items: [...] }
```

Each item in `items[]` has exactly this shape (see `public/data/hsk/1.json`):

```json
{ "level": 1, "hanzi": "爱", "trad": "愛", "pinyin": "ài", "pinyinNumeric": "ai4", "english": "love" }
```

The pipeline that produces these files is `scripts/build-data.mjs` → `buildHsk()` (lines 427–456). It downloads the upstream TSV from `hskhsk.com` (MIT licence, see `CREDITS.md` §4), parses tab-separated lines, and writes one JSON per level plus `index.json`. To refresh or add HSK 3.0 lists: drop new JSON files in the same shape and update `index.json.levels`.

### Lesson structure (not implemented yet)

The Learn screen is a hub at `src/screens/learn.js` (exports `titleKey` + `render(container, ctx)`; `#/learn` shows the area menu, `#/learn/<area>` hands off to `src/learn/<area>.js`). The hash router (`src/router.js`) delivers segments: a deep link `#/learn/hsk3/lesson-5` arrives as:

```js
ctx.route = {
  name: 'learn',
  segments: ['hsk3', 'lesson-5'],
  params: {},
  path: 'hsk3/lesson-5'
}
```

**Proposed lesson breakdown** (one file per lesson, lazy-loaded):

```
public/data/lessons/
├── index.json                          // { levels: { hsk1: [...], hsk2: [...] } }
├── hsk1/
│   ├── lesson-1.json                   // { level: 1, lesson: 1, titleKey, words: ["爱","八",...], sentences: [id...] }
│   └── ...
├── hsk2/
│   ├── lesson-1.json
│   └── ...
└── ...
```

Each lesson references word IDs from `hsk/{level}.json` and sentence IDs from `public/data/sentences/` (already generated by `build-data.mjs`). The Learn screen would:

1. Load `public/data/lessons/index.json` → build the level/lesson menu.
2. On `#/learn/hskN/lesson-M`, fetch `public/data/lessons/hskN/lesson-M.json`.
3. For each word, pull the full entry from `public/data/hsk/N.json` (or a sharded index if we split HSK later).
4. Use existing `src/speech.js` (`speak(text, {lang:'zh-CN'})`) for TTS.
5. Persist progress via `storage.set('progress', 'hsk3-lesson-5', { done: true, score: 87 })`.

## (b) Optional login / sync — hook is already in `src/storage.js`

### Extension points (already present)

1. **`createStorage(driver)`** (lines 206–223): accepts any object with `{ get, set, remove, list, name }`. The default export wraps `lazyDriver()` which picks IndexedDB → localStorage → memory. A sync driver can wrap the chosen local driver and replicate writes to a server.

2. **`onWrite(fn)`** (lines 229–233): registers a callback fired **after every successful local write**. The callback receives `{ store, key, value }`. The default export already wraps `set()` to call all hooks (lines 236–249). A sync layer registers its push logic here.

```js
// Example: a future sync module would do
import storage, { onWrite } from './storage.js';

onWrite(async ({ store, key, value }) => {
  if (store === 'settings' && key === 'locale') return; // skip trivial
  await syncClient.push({ store, key, value, ts: Date.now() });
});
```

3. **Driver interface** (lines 34–50, 53–98, 122–155): `memoryDriver`, `localStorageDriver`, `idbDriver` all implement the same four async methods. A remote driver implements the same interface.

### Free self-hosted options

| Option | Why it fits | Notes |
|--------|-------------|-------|
| **PocketBase** (Go + SQLite, single binary) | Auth (email/password, OAuth), realtime subscriptions, file storage, admin UI; runs on any Linux box; ~20 MB binary | `npx pocketbase serve --http=0.0.0.0:8090` on the homelab; clients talk REST + WebSocket. |
| **SQLite + custom HTTP** (e.g. `bun`/`node` + `better-sqlite3`) | Zero-dep, full control, trivial backup (`.dump`) | More boilerplate for auth/realtime. |
| **Supabase (self-hosted)** | Postgres + Auth + Realtime + Storage | Heavier (Docker stack), overkill for a single-user PWA. |

**Recommendation:** PocketBase. One binary, built-in user accounts, email verification, and realtime sync — the app only needs to replicate the five stores (`meta`, `settings`, `srs`, `progress`, `gamification`).

### Minimal data schema (PocketBase collections)

```sql
-- users: handled by PocketBase auth (email, password hash, verified, ...)
CREATE TABLE sync_changes (
  id TEXT PRIMARY KEY,           -- uuid
  user TEXT NOT NULL,            -- PocketBase user id
  store TEXT NOT NULL,           -- 'meta' | 'settings' | 'srs' | 'progress' | 'gamification'
  key TEXT NOT NULL,
  value TEXT NOT NULL,           -- JSON string
  client_ts INTEGER NOT NULL,    -- Date.now() from client
  server_ts INTEGER NOT NULL,    -- server receipt time
  deleted INTEGER DEFAULT 0,     -- 1 = tombstone
  UNIQUE(user, store, key)
);
CREATE INDEX idx_sync_user_store ON sync_changes(user, store);
```

Client sync protocol (simplified):

1. On login, `GET /api/collections/sync_changes/records?filter=user="<id>"` → full state.
2. Apply locally via `storage.set(store, key, JSON.parse(value))` (skip if local `client_ts` newer).
3. Register `onWrite` hook → `POST /api/collections/sync_changes/records` with `{ user, store, key, value: JSON.stringify(value), client_ts: Date.now(), deleted: 0 }`.
4. On delete → same with `deleted: 1`.
5. Realtime: subscribe to `sync_changes` changes for `user=<id>` → apply remote writes.

### Conflict resolution

- **Last-write-wins by `client_ts`** (simple, works for single-user multi-device).
- **Per-store policy** (configurable later):
  - `settings` / `meta`: LWW.
  - `srs` / `progress` / `gamification`: merge by `key` (each card/progress entry independent); if same key edited on two devices, keep higher `reps`/`score` or newer `client_ts`.
- **Tombstones**: `deleted: 1` wins over any older write.

## (c) Android app with Capacitor — no rewrite needed

### Why it works out of the box

- The app is **static ES modules** with **relative paths only** (`./src/...`, `./data/...`). `scripts/build.mjs` copies everything to `dist/` preserving structure.
- `index.html` loads `<script type="module" src="./src/main.js">` — works from any origin (`file://`, `capacitor://`, `https://`).
- Service worker (`sw.js`) uses relative paths (`./`, `./data/...`) and is stamped with a content hash at build time (`scripts/build.mjs` lines 78–89).
- No backend, no Node runtime, no bundler.

### Capacitor commands (tested via `--help`)

```bash
# 1. Install Capacitor CLI and Android core (one-time, in the repo root)
npm i -D @capacitor/cli @capacitor/android

# 2. Initialize (creates capacitor.config.json, android/ folder)
npx cap init chino-app com.example.chino --web-dir=dist

# 3. Add Android platform
npx cap add android

# 4. Build the web assets (must run before every cap copy/sync)
npm run build

# 5. Copy web assets into the Android project
npx cap copy android

# 6. Open Android Studio (for signing, emulators, device run)
npx cap open android
```

**Key `capacitor.config.json` settings** (generated by `cap init`, adjust as needed):

```json
{
  "appId": "com.example.chino",
  "appName": "Chino",
  "webDir": "dist",
  "server": { "androidScheme": "https" },
  "android": { "allowMixedContent": true, "captureInput": true }
}
```

- `androidScheme: "https"` makes the WebView treat `https://` assets as secure (required for Service Worker, Web Speech API, IndexedDB).
- `allowMixedContent: true` lets the WebView load `http://` resources if any (not used here, but harmless).
- `captureInput: true` enables the soft keyboard for any `<input>` (not used in shell, but future screens may).

## (d) Translate to another language — drop-in mechanism

The i18n system (`src/i18n.js`) is designed for **zero-code language adds**:

1. Copy `src/locales/en.json` → `src/locales/<code>.json` (e.g. `es.json`).
2. Translate **every value**; keep keys identical.
3. Set `"locale.name": "Español"` (the language’s own name) in the new file.
4. Add the code to `src/locales/index.json`: `["en", "es"]`.
5. Rebuild: `npm run build` → manifest.webmanifest picks up the new locale automatically (see `scripts/manifest.mjs`).

**That is all.** Boot (`src/main.js` line 109) calls `loadAvailableLocales()` which fetches every code listed in `index.json`. The language picker is already wired: the Profile screen (`src/extras/profile.js`) lists them via `availableLocales()` and `localeLabel(code)`.

No string literals in code — every UI text comes from `t('key')` (see `src/i18n.js` line 166). Interpolation: `t('greet', { name })` with `"greet": "Hello {name}"`.
